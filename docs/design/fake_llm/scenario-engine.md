# 场景引擎

## 概述

场景引擎是 Fake LLM Server 的决策核心：按测试者声明的场景文件，把每个进入的协议请求解析为请求特征、匹配到唯一场景、推进多轮游标，产出确定性的响应决策（响应形状 + 错误注入 + 延迟注入），交投递层执行。

## 架构

### 场景声明

测试者通过场景文件声明「给定请求特征 → 返回什么响应」。场景是唯一控制面——Fake LLM Server 的所有行为都来自场景，无内建的隐式行为。场景格式与集成测试共用同一套定义：同一份场景文件既可驱动集成测试，也可驱动黑盒端到端测试，测试者无需为两种测试形态各写一份。

场景声明的主要维度：

| 维度 | 说明 |
|------|------|
| 匹配条件 | 请求特征匹配规则（模型 ID、消息内容片段、工具定义、参数） |
| 响应形状 | 七类形状之一（见下）+ 逐轮编排 |
| 投递控制 | 流式分段与间隔、错误注入、延迟注入（声明详见 [delivery](delivery.md)） |
| 缓存控制 | 自动模拟或逐轮显式注入（详见 [kv-cache-simulation](kv-cache-simulation.md)） |

### 请求特征匹配

进入的请求先解出协议无关的请求特征，再与场景的匹配条件比对，**命中唯一场景**。匹配条件支持按模型 ID、消息内容片段、工具定义、请求参数的组合；无匹配条件的场景为兜底场景。同一请求命中多个场景视为场景文件错误，测试启动时即失败——不允许运行期的模糊匹配。

### 匹配结构与性能

场景匹配的响应时间不随场景数量增长：请求特征匹配按「模型 ID + 协议」先索引到场景组，再在组内比对匹配条件——索引查找为常数时间，组内比对只发生在同模型同协议的少量场景之间。场景文件的数量增长只增加索引条目，不增加单次请求的比对次数。

一个场景可声明多轮响应序列（`turns` 结构），按会话粒度推进：同一会话的第 N 次请求返回第 N 轮响应。游标随场景状态存储，会话结束后状态销毁。超出声明轮次时视为场景文件错误，立即失败并报告——不静默循环或回退，保证测试确定性。

会话的识别不依赖协议外信息：对话协议的请求中不携带会话标识，会话身份由消息历史序列本身定义——完整 messages 数组构成一条增长链，新请求的历史包含且超过已记录的历史即视为同一会话的下一轮。这带来一个显式边界：两个并发会话若消息前缀完全相同（如各自首轮都是同一条用户消息），在协议层面不可区分，会被视为同一会话流推进游标——并发多会话测试通过不同的首轮消息内容或不同的模型 ID 消歧（场景匹配条件本就支持按内容与模型区分）。这一前缀重合语义同时是 KV cache 模拟的输入：真实供应商同样无会话概念、纯按前缀匹配，前缀重合的并发会话共享缓存状态恰是真实行为（详见 [kv-cache-simulation](kv-cache-simulation.md)）。

### 响应形状

场景引擎产出七类协议无关的响应形状，由协议层按 [protocol-mapping](../llm/protocol-mapping.md) 的映射反向序列化为对应协议的原生字段：

| 形状 | 内容 | 验证的 CloseClaw 能力 |
|------|------|---------------------|
| 文本回复 | 纯文本内容块 | 基础对话与内容归一化 |
| 推理/思考 | 推理内容（含强度档位可配）+ 文本 | 推理可见性、推理强度档位、Thinking 块管理 |
| 工具调用 | 单个或并行工具调用请求 | 工具调用解析、多轮工具回传 |
| 流式输出 | 响应以流式形态投递（分段粒度、段间间隔可控） | 流式解析、实时展示、中断处理 |
| 错误 | HTTP 错误或流中断 | 重试与回退逻辑 |
| 延迟 | 首 token / 逐段 / 整体延迟 | 超时与回退路径 |
| token 用量 | 用量字段组合（可缺失部分字段） | 用量统计与显示 |

形状可组合：一次响应可以是「推理 + 工具调用 + 流式 + 用量」的组合，覆盖多轮工具调用回传（工具结果作为下一轮请求进入时，场景按 `turns` 推进给出下一轮响应）与并行工具调用（一个响应含多个工具调用块）。

推理/思考的协议表示：OpenAI 协议产出 `reasoning_content` 独立字段，Anthropic 协议产出 thinking 内容块（含 signature 签名）。强度档位由场景声明（low/medium/high），请求中带推理参数时按场景声明的档位产出对应长度的推理内容——供应商特有推理行为（无法关闭、强制回传）不在本层模拟，由供应商 fixture 覆盖。

### 用量形状

token 用量作为响应的独立维度，字段覆盖输入、输出、推理消耗、缓存命中、缓存写入，各字段可按场景配置且支持逐轮变化。字段可缺失——模拟不返回缓存字段（或推理字段）的响应，验证 CloseClaw 对缺失字段的显示行为（对应 [llm 需求 F9](../../requirements/llm.md) 的用量统计）。各字段在两种协议中的原生位置以 [llm/protocol-mapping](../llm/protocol-mapping.md) 的用量字段形状表为权威。缓存命中/写入字段的取值默认由 KV cache 模拟状态机推导，也可显式注入覆盖（详见 [kv-cache-simulation](kv-cache-simulation.md)）。

## 数据流

```
协议端点层交付请求特征
  → 特征匹配 → 命中唯一场景（多命中为场景文件错误，零命中走兜底场景）
  → 会话识别（消息历史公共前缀）→ 多轮游标推进
  → 取当前轮次声明的响应形状
    ├─ 用量字段：KV cache 模拟推导（默认）或显式注入覆盖
    ├─ 投递控制：错误/延迟/流式参数原样携带
    └─ 组合形状展开为内容块序列
  → 决策（形状 + 内容块 + 用量 + 投递控制）交协议层序列化
  → [delivery](delivery.md) 执行投递
```

## 模块关系

- **模块内上游**：[endpoints](endpoints.md)（协议层解出请求特征后调用）
- **模块内下游**：[delivery](delivery.md)（决策交付执行）、[kv-cache-simulation](kv-cache-simulation.md)（缓存字段推导）
- **跨模块**：响应形状的双协议序列化锚定 [llm/protocol-mapping](../llm/protocol-mapping.md)；场景中的响应对象以 [fixtures](fixtures.md) 的协议基线为形状来源；多轮游标依赖 CloseClaw 侧「消息历史只追加不重写」的前缀稳定性原则（定义于 [llm](../llm/README.md)）
