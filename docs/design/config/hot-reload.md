# hot-reload

## 概述

配置热重载使 CloseClaw 在运行时修改配置文件后自动生效，无需重启 daemon 或中断已有会话。监听配置目录文件变更，增量重载变更文件，校验通过后更新内存并通过事件通道通知各消费模块。各模块自行决定是否重载及何时采纳新配置。

## 架构

### 核心机制

热重载由 ConfigReloadManager 驱动，包含三个核心环节：

- **文件监听**：通过文件系统事件监听配置目录变更，去抖合并短时间内的多次变更，避免频繁重载。监听范围覆盖 `config/` 目录下的业务配置文件，以及其子目录 `credentials/`（凭据目录，按供应商分文件独立存放）——凭据文件变更同样被纳入检测，为「重启生效」类的凭据变更提供触发入口。
- **增量重载**：仅解析和重载发生变更的配置文件，不重新加载整个配置目录。agents.json 的变更同样通过 ConfigReloadManager 处理——变更通知到达后，AgentDirectoryProvider 根据最新注册清单重新扫描 agents/ 目录，重新合并并补齐默认值。credentials/ 目录的文件变更不触发凭据的即时重载，而是按「重启生效」语义进入待重启暂存区（见下文「重启类变更确认与触发」）。
- **校验失败处理**：新配置校验通过后更新内存。校验或解析失败时，保留内存中的旧配置继续运行，不恢复备份文件，记录错误日志并通过 IM 推送通知 Owner。若该配置为运行期间新增、从未成功加载过（内存中无旧值），阻塞该配置的加载及依赖该配置的后续流程。

### 变更通知

配置更新后，ConfigReloadManager 通过事件通道向所有订阅的消费模块发送变更通知。通知携带变更文件路径，各消费模块自行决定是否重载及何时采纳新配置。

配置变更的生效时机由各消费模块决定，不由配置模块统一控制。按生效机制分为三类（需求 [config §F7](../../requirements/config.md) 与各模块文档定义归属，本文档从触发侧描述机制）：

- **即时生效**：模块收到通知后立即重载（如权限模块）
- **边界生效**：变更在某个使用边界统一生效——已存在会话保持旧配置、新创建的会话使用新配置（如会话参数），或下一次 System Prompt 组装、下一次周期任务扫描触发（如技能、日志、记忆配置）
- **重启生效**：变更须重启 Gateway 方可生效，重启前按旧配置运行（如机器人绑定、模型与凭据、平台启用清单）

新增会话直接从 ConfigManager 读取最新配置，不受热重载通知流程影响（重启生效类配置除外——重启执行前新会话仍读旧值）。

**重启类变更确认与触发**：对重启生效类配置，配置模块在校验通过后将新值写入「待重启暂存区」而**不立即覆盖运行时内存**——ConfigManager 在重启执行前仍暴露旧配置（新会话、API 查询、间接读取均取旧值），与「系统按旧配置运行」一致。同时将本模块置为「待重启」状态并携带变更信息触发网关择机重启；重启执行时机与边界由 [daemon §F6](../../requirements/daemon.md)（配置触发的网关重启）协调，重启完成后方将暂存新值切换为运行时配置。消费方对这类通知不做立即重载。

### 去抖策略

文件变更事件可能在短时间内密集到达（如编辑器的多次保存）。ConfigReloadManager 维护去抖窗口，窗口内收到的变更事件合并处理，窗口结束后执行一次重载。

## 数据流

```
1. 文件变更事件触发
   → ConfigReloadManager 去抖合并短时间内的多次变更

2. 读取所有变更文件内容

3. 校验新配置
   - 校验通过 → 更新内存中的配置缓存 → 进入步骤 4
     （重启生效类例外：不使用运行时内存更新，校验通过的新值写入「待重启暂存区」，ConfigManager 仍暴露旧值，见架构「重启类变更确认与触发」）
   - 校验失败 → 保留内存旧配置，记录错误，IM 推送通知 Owner
     - 有旧值 → 继续使用旧配置运行，流程结束
     - 无旧值 → 阻塞该配置加载及依赖该配置的后续流程，流程结束

4. 通过事件通道发送变更通知（携带变更文件路径）

5. 各消费模块接收通知 → 自行决定重载策略
   - 即时生效 → 立即重载本地配置引用
   - 边界生效 → 标记配置已更新，在边界点生效（新会话创建 / 下一次 System Prompt 组装 / 下一次周期任务扫描）
   - 重启生效 → 不立即重载；配置模块完成变更确认后触发网关择机重启（执行见 daemon §F6），重启完成后暂存新值切换为运行时配置生效

新会话创建时不走热重载流程，直接从 ConfigManager 读取最新配置（重启类配置除外——重启前仍读旧值）。
```

## 模块关系

- **上游**：ConfigManager（所有配置加载成功后注册热重载监听器，注册后才进入运行状态）、文件系统（触发变更事件）
- **下游**：各消费配置的模块通过 ConfigReloadManager 的 pub/sub 事件通道接收变更通知，自行决定重载策略。哪些模块订阅、各模块如何响应变更，是各模块自身的设计决策。
  > 本文档从 ConfigReloadManager 子组件视角描述关系。从配置模块整体看，消费方通过不同方式获取配置数据——API 查询、文件延迟读取、事件通道订阅，详见 config/README.md 模块关系节。
- **与 ConfigManager 的关系**：ConfigReloadManager 负责运行时变更处理，ConfigManager 负责启动时加载和写入接口。ConfigManager 启动时通过其 BackupManager 组件（滚动备份管理，启动时回退损坏文件）恢复损坏配置；ConfigReloadManager 热重载校验失败时不回退备份，仅保留内存旧配置并通知 Owner。
- **无关**：processor_chain、tools、skills（不直接依赖热重载，通过上层模块间接使用更新后的配置）
