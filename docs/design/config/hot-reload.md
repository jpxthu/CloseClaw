# hot-reload

## 概述

配置热重载使 CloseClaw 在运行时修改配置文件后按各配置项的生效类别自动生效：即时生效类重载后立即生效，边界生效类在各自使用边界生效（无需重启），重启生效类由 Daemon 择机执行网关重建后生效，均无需 Owner 手动操作。监听配置目录文件变更，增量重载变更文件，校验通过后更新内存并通过事件通道通知各消费模块。各模块自行决定是否重载及何时采纳新配置。

## 架构

### 核心机制

热重载由 ConfigReloadManager 驱动，包含三个核心环节：

- **文件监听**：通过文件系统事件监听配置目录变更，去抖合并短时间内的多次变更，避免频繁重载。监听范围（按配置根目录相对路径）覆盖：`config/` 下的各业务配置文件、`config/permissions.json`、`config/credentials/` 下的凭据文件、`agents/<agent-id>/config.json` 与 `agents/<agent-id>/permissions.json`（`config/` 与 `agents/` 是配置根目录下的同级子目录）；`.backups/` 目录不在监听范围，备份写入不会触发重载。凭据文件变更被纳入检测，为重启生效类的凭据变更提供触发入口；权限配置文件只产生变更信号（分工见 [README](README.md) 配置目录结构说明）。
- **增量重载**：仅解析和重载发生变更的配置文件，不重新加载整个配置目录。agents.json 的变更同样通过 ConfigReloadManager 处理——变更通知到达后，AgentDirectoryProvider 根据最新注册清单重新扫描 agents/ 目录并补齐默认值；`agents/<agent-id>/config.json` 的变更走同一路径（按最新注册清单重扫并补齐默认值），`agents/<agent-id>/permissions.json` 的变更通知转交权限模块。运行期重扫时：注册 ID 无 config.json → 记 WARN 跳过；config.json 损坏 → 保留该 Agent 上次加载结果并通知 Owner（运行期不恢复备份文件）；从未成功加载过的 Agent 配置损坏 → 阻塞依赖该 Agent 配置的功能并通知 Owner（运行期不因此拒绝启动）。Agent 配置与注册清单的加载层更新不改变生效边界：运行中的 Session 仍按旧配置，下一次新建 Session 才采用新值。credentials/ 目录的文件变更不触发凭据的即时重载，而是按重启生效类进入待重启暂存区（见下文「重启类变更确认与触发」）。
- **校验失败处理**：新配置校验通过后更新内存。校验或解析失败时，保留内存中的旧配置继续运行，不恢复备份文件（Agent 配置文件的运行期损坏按「增量重载」的处置：保留上次加载结果、不恢复备份），记录错误日志并发布失败事件，由 Daemon 经 Gateway 系统通知接口推送 Owner。若该配置为运行期间新增、从未成功加载过（内存中无旧值），阻塞该配置的加载及依赖该配置的后续流程；权限配置文件的容错由权限模块自管，不适用本条的阻塞语义（见 [权限配置管理](../permission/permission-configuration.md)）。

### 变更通知

变更校验完成、内存中的生效配置确定后，ConfigReloadManager 通过事件通道发送变更通知（携带变更文件路径）；重启生效类的运行时内存未更新（新值只在暂存区），这类通知不含「内存已更新」的含义。各消费模块自行决定是否订阅及何时采纳新配置。

配置变更的生效时机由各消费模块决定，不由配置模块统一控制。按生效类别分为三类（需求 [config §F7](../../requirements/config.md) 与各模块文档定义归属，本文档从触发侧描述机制）：

- **即时生效类**：消费方收到通知后立即重载（如权限配置——权限模块重载规则与沙盒模式，下一次权限评估即使用新值）；本模块自身的即时生效项（IM 用户↔User 绑定）由本模块重建身份映射快照，下一次消息解析即使用新绑定
- **边界生效类**：变更在某个使用边界统一生效——已存在会话保持旧配置、新创建的会话使用新配置（如 Agent 配置与注册清单；会话配置中按会话快照读取的部分同样以新会话为边界），或下一次统一扫描/触发时对同一 Agent 下全部会话统一生效（如 Session 生命周期扫描参数；记忆配置按下次触发，含消息级与周期扫描），或下一次 System Prompt 组装触发（如技能目录与清单）；日志级别自下一条日志起生效、保留天数自下一次清理起生效；workflow 定义由 workflow 模块在流程启动时读取，同样属边界生效
- **重启生效类**：变更须重启 Gateway 方可生效，重启前按旧配置运行（如机器人↔Agent 绑定、模型与凭据、渠道配置、插件列表、Gateway 服务参数——均属支撑 Gateway 服务运行的配置）

新增会话直接从 ConfigManager 读取最新配置，不受热重载通知流程影响（重启生效类配置除外——重启执行前新会话仍读旧值）。

同一文件内的字段分属不同生效类别时，按字段各自类别分别处理（即时部分立即重载并通知，重启部分进入待重启暂存区）——此时「重启前仍暴露旧值」只约束重启生效类字段，同一文件中已即时生效的字段对外即为新值。

**重启类变更确认与触发**：对重启生效类配置，配置模块在校验通过后（上一份生效内容此刻存入备份）将新值写入「待重启暂存区」而**不立即覆盖运行时内存**；后续同一文件的变更若校验失败，暂存区内容保持不变、仅记录错误并通知 Owner——ConfigManager 在重启执行前仍暴露旧配置（新会话、API 查询、间接读取均取旧值），与「系统按旧配置运行」一致。同时把待生效变更交给 Daemon：Daemon 进入待重启状态并记录待生效变更，择机执行重建；时机与边界见 [daemon §F6](../../requirements/daemon.md)（配置触发的网关重启）。

切换点在重建之后：Daemon 以暂存变更信息驱动重建——重建出的组件按暂存新值装配，而 ConfigManager 对一般读取方（新会话、API 查询、间接读取）仍暂暴露旧值，与「重启执行前按旧配置运行」一致。重建成功后，配置模块将本次待执行集合对应的暂存新值切换为运行时配置；重建失败则丢弃本次装配结果、旧组件与旧配置继续运行，未切换的变更保留在暂存区待下次窗口（重建与失败兜底见 [daemon 重启](../daemon/restart.md)）。消费方对这类通知不做立即重载。

### 去抖策略

文件变更事件可能在短时间内密集到达（如编辑器的多次保存）。ConfigReloadManager 维护去抖窗口，窗口内收到的变更事件合并处理，窗口结束后执行一次重载。经配置写入接口的连续多次写入按同一去抖窗口合并为一次重载；写入产生的文件变更事件按同一次变更识别，不重复通知、不重复触发重启。

## 数据流

```
1. 文件变更事件触发
   → ConfigReloadManager 去抖合并短时间内的多次变更

2. 读取变更文件内容
   - 业务配置、凭据文件与 Agent 配置 → 进入步骤 3（凭据文件按重启生效类写入暂存区）
   - 权限配置文件（`config/permissions.json`、`agents/<agent-id>/permissions.json`）→ 不解析、不校验，直接进入步骤 4

3. 校验新配置
   - 校验通过 → 上一份生效内容存入备份 → 更新内存中的配置缓存 → 进入步骤 4
     （重启生效类例外：不使用运行时内存更新，校验通过的新值写入「待重启暂存区」，ConfigManager 仍暴露旧值，见架构「重启类变更确认与触发」）
   - 校验失败 → 保留内存旧配置，记录错误，发布失败事件（由 Daemon 经 Gateway 系统通知接口推送 Owner）
     - 有旧值 → 继续使用旧配置运行，流程结束
     - 无旧值 → 阻塞该配置加载及依赖该配置的后续流程，流程结束

4. 通过事件通道发送变更通知（携带变更文件路径）；边界生效类消费方不订阅，在其边界点现读内存中的最新值

5. 各消费模块接收通知 → 自行决定重载策略
   - 即时生效类 → 消费方立即重载本地配置引用（权限模块重载权限配置；IM 用户↔User 绑定由本模块重建身份映射快照。校验失败时消费方保留旧配置并按各自机制通知 Owner，见 [权限配置管理](../permission/permission-configuration.md)）
   - 边界生效类 → 无需通知驱动：内存已更新，消费方在各自边界点读取最新值（新会话创建 / 下一次 System Prompt 组装 / 下一次周期任务扫描）
   - Agent 配置与注册清单变更 → AgentDirectoryProvider 重扫 agents/ 目录，重扫结果交由 Daemon 触发 AgentRegistry 替换（生效边界仍为下一次新建 Session；其中 per-agent memory 覆盖段按记忆模块的下次触发生效）
   - 重启生效类 → 不立即重载；配置模块完成变更确认后触发网关择机重启（执行见 daemon §F6）；重建出的组件按暂存新值装配、重建成功后切换暂存新值为运行时配置，重建失败则丢弃本次装配、旧配置继续运行

新会话创建时不走热重载流程，直接从 ConfigManager 读取最新配置（重启生效类配置除外——重启前仍读旧值）。
```

## 模块关系

- **上游**：ConfigManager（所有配置加载成功后注册热重载监听器，注册后才进入运行状态）、Daemon（作为后台任务装配与启停本子功能）、文件系统（触发变更事件）
- **下游**：Daemon（订阅变更事件并执行择机重启、订阅失败事件并转发 Owner 提示）、各消费配置的模块（通过事件通道接收变更通知，自行决定重载策略）——模块级消费关系见 [README](README.md) 模块关系节。
  > 本文档从 ConfigReloadManager 子组件视角描述关系。从配置模块整体看，消费方通过不同方式获取配置数据——API 查询、文件延迟读取、事件通道订阅，详见 config/README.md 模块关系节。
- **与 ConfigManager 的关系**：ConfigReloadManager 负责运行时变更处理，ConfigManager 负责启动时加载和写入接口。ConfigManager 启动时通过其 BackupManager 组件（滚动备份管理，启动时回退损坏文件）恢复损坏配置；ConfigReloadManager 热重载校验失败时不回退备份，仅保留内存旧配置并发布失败事件（由 Daemon 转发 Owner 提示）。
- **无关**：processor_chain、tools（不直接依赖热重载，通过上层模块间接使用更新后的配置；skills 的 extraDirs 经 config 的配置查询取得，不订阅变更通知）
