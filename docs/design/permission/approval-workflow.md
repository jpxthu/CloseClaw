# 审批工作流

## 概述

当操作被权限引擎判定为 Deny，或新用户注册请求需要 Owner 决策时，不直接阻断——进入审批工作流，由 Owner 决定单次放行、加入白名单或拒绝。

## 架构

### 审批分流

不同场景的处理方式不同：

| 场景 | 处理 |
|------|------|
| 子 Session 操作 | 静默 Deny，不进入审批 |
| 心跳任务 | 按任务配置静默跳过或通知 Owner；不进入审批 |
| 黑名单命令 | 直接 Deny，不进入审批 |
| 命令安全解析为 malicious | 直接拦截并通知 Owner，不进入权限审批 |
| 命令安全解析为 uncertain | 进入审批 |
| 沙盒不可用 | 受沙盒约束的操作直接 Deny，不进入审批 |
| `whitelist` 模式下白名单外命令 | 直接 Deny，不进入审批 |
| 心跳任务的 User 未配置或未注册 | 跳过任务并通知 Owner，不进入审批 |
| `sandbox` 模式下白名单外 trusted 命令 | 沙盒内执行，不进入审批 |
| 文件类工具越界 | 进入审批（与其它 Deny 同一队列） |
| 网络访问 Deny | 进入审批；与移出沙盒同次时合并一张卡片 |
| spawn / steer / kill 被拒（父 Session 发起的请求） | 进入审批 |
| 权限配置目录访问（非当前 Agent 文件） | 直接 Deny，不进入审批 |
| 权限配置文件读取（当前 Agent） | 进入审批，仅单次放行/拒绝 |
| 权限配置文件写入 | 直接 Deny，不进入审批 |
| 命中硬编码高风险名单（即使规则 Allow） | 进入审批，只能单次放行/拒绝 |
| 其他 Deny | 进入审批 |

### 审批队列

审批请求由守护进程内的审批队列（ApprovalFlow）管理：

- **入队**：操作被 Deny 或命中硬编码高风险名单 → 创建审批请求入队 → 工具调用进入等待状态；审批等待中的前台工具调用保持 Pending，Session 因此按 Busy 处理，同轮其他工具可先执行。审批等待属于 [common PermissionGate](../common/core-traits.md#permissiongate) 调用内部的实现细节，调用方看到的是一次同步判定。
- **审批 ID**：在请求所属的 Session 内从 1 起递增，每个 Session 独立计数；同一 Session 内不复用已分配的审批 ID。审批指令的 Session 上下文由消息通道提供——在哪个对话中发审批，就作用于哪个 Session 的审批 ID 空间；卡片与指令必须属于同一 Session，Owner 在其他对话发指令无法审批该 Session 的请求。
- **标识命名**：操作审批用「审批 ID」（Session 内整数）；注册请求用「request_id」（队列 string）；回调按各自 ID 关联。
- **去重**：同一 Agent-User 组合下、操作类型与参数相同的请求已有等待中的实例 → 直接返回 Deny，不分配审批 ID、不重复推送审批。去重作用于请求本身，与审批 ID 的计数空间无关。审批完成或超时后，该操作的重复申请限制解除，Agent 可重新发起。
- **等待与超时**：默认等待 5 分钟（可配置）；超时未响应则自动向 Agent 返回拒绝结果。超时后 Owner 再对该 ID 发审批指令，系统返回「该审批已超时」。
- **回调**：Owner 审批后按请求 ID 关联等待中的判定调用，使其以 Allow 或 Deny 返回；无独立回调接口。等待方已不可用（会话终止/进程退出）时，请求以 Deny 结束。
- **可捕获的关闭流程**：所有等待中的请求以 Deny 结束并通知对应 Agent。进程崩溃/重启后内存队列本身不存在；Session 恢复时按 [session 恢复机制](../session/session-recovery.md) 对挂起的工具调用注入失败结果，不依赖队列残留。
- **Owner 离线**：请求照常计时；超时后不补推，Owner 可查历史审批记录；不阻塞系统其他功能。

审批队列同时承载新用户注册请求（UserCreationRequest），但注册请求是**卡片专属**，不走操作审批的三选一决策：

- 注册请求只通过审批卡片呈现与确认；`request_id` 是队列关联标识，与操作审批的 Session 内审批 ID 是两套空间，审批指令不用于寻址注册请求。
- Owner 的决策是确认或调整 InitialPermissionSet，不是单次放行/加入白名单/拒绝。
- 同一用户已有等待中的注册请求时直接拒绝新请求；审批通过后由 Gateway 权限指令处理层生成 UserRegistration，权限系统消费并落盘用户记录与规则。

> **与 PermissionGate 的关系**：审批入口只有一个——消费方（tools / session / gateway）经 [common PermissionGate](../common/core-traits.md#permissiongate) 发起判定，权限引擎在实现内部把需审批的 Deny 入队并挂起直至有结论；审批队列（ApprovalFlow）不对外暴露独立接口。子 Session、心跳、黑名单等按分流表排除后不产生队列项。

审批队列为内存结构，不阻塞系统其他功能；无 Owner 在线时系统保持可用。

### 审批信息

审批请求入队后立即推送 Owner 的 IM 渠道，不批量延迟。推送的审批信息包含：

- 发起操作的 Agent ID
- 当前 User ID（本轮 caller）
- 操作类型和参数（路径、命令、目标等）
- 风险等级提示
- 审批请求 ID
- 命令类操作附 Agent 提供的命令用途说明；命令安全解析为 uncertain 时另附原始命令、解析失败原因与风险标签。

移出沙盒执行的请求额外标明「移出沙盒执行」、用途说明与所需网络访问范围。

风险等级（RiskLevel）只是卡片上的提示，不决定审批触发；命中硬编码高风险名单的操作即使规则 Allow 也进入审批，且只能单次放行/拒绝。

### Owner 决策

所有审批请求只推送给 Owner；非 Owner 用户没有审批权力，其审批指令由 Gateway 直接拒绝。Owner 可通过审批卡片或审批指令表达决策，两条路径走同一审批处理逻辑。Owner 可选择：

- **单次放行**：仅本次操作放行，不持久化规则，后续相同操作仍需重新审批。
- **加入白名单**：写入持久化规则，后续同类操作按新规则评估。
- **拒绝**：操作被 Deny。

Owner 可按 Agent 维度和 User 维度分别决策：

- 只放行触发操作的 Agent、只放行当前 User 上下文、或两者均放行。
- 单次放行按所选维度注入一次性 Allow；未选维度按当前规则评估；非 Owner caller 两维度都 Allow 才执行，Owner caller 只评估 Agent 维度。默认配置下仅放行一个维度可能仍被另一维拒绝，Owner 需选择两者或确认另一维已允许。
- 加入白名单按所选维度写入规则；命令白名单是 Agent 维度资产，User 维度不覆盖，移出沙盒的加入白名单不按 Agent/User 维度拆分。
- **Owner 自身调用被拦截时，只评估 Agent 维度（User 维度已豁免），不存在 User 维度决策。**
- 审批指令路径固定按两个维度处理；卡片路径可选择单一维度，两条路径共用审批处理逻辑。

移出沙盒执行的「加入白名单」写入命令白名单，表示该命令后续可在宿主执行，不是普通权限规则（见 [沙盒](sandbox.md#移出沙盒执行)）。
移出沙盒执行的「单次放行」只改变本次执行位置，不向规则层注入 Allow（见 [沙盒](sandbox.md#移出沙盒执行)）。
非工具操作的审批恢复：斜杠命令类 Deny 由 Gateway 挂起 SlashResult，审批通过后由 Gateway 重放执行并回发结果；收发消息 Deny 由 Gateway 挂起消息，审批通过后重新投递；不依赖 Session 工具挂起。

权限配置文件读取的单次放行是硬编码保护的一次性例外，不按 Agent/User 维度拆分，也不写入规则；卡片对该类请求只提供单次放行/拒绝，写入不提供放行。
单次放行有三种落点：一般操作注入一次性 Allow；移出沙盒只改变本次执行位置；权限配置文件读取只放行本次读取。

### 高风险操作

标注为高风险（命中硬编码高风险名单）的操作有额外限制：即使规则 Allow 也进入审批，永远只能单次放行，不能被加入白名单。风险等级（RiskLevel）只是卡片上的提示，不决定是否属于高风险名单。

- 高风险操作以硬编码名单维护，至少包含：版本控制目录读写、权限配置文件读取、系统配置文件写入、破坏性删除命令等。
- 审批卡片不显示「加入白名单」选项；审批指令路径对高风险操作同样拒绝加入白名单。
- 风险等级不改变审批触发条件，只限制可选决策。

### 规则变更与审批

审批请求**不记录规则版本快照**。Owner 作出决策后，系统按当前生效规则处理该操作：

- **单次放行**：在本次评估中按 Owner 选择的维度注入一次 Allow，仅对本次操作有效；不写入规则（移出沙盒与权限配置文件读取除外，见各自例外）。
- **加入白名单**：先把规则写入当前规则集，再按新规则评估后续操作。
- **拒绝**：本次操作 Deny。

等待期间规则变更立即影响本次决策所依据的规则集，不存在「按旧规则放行」的窗口期；规则变更也不会使已入队的请求失效，Owner 仍可对该请求作出决策。

### 调试日志

- 审批请求的创建、推送、单次放行、加入白名单、拒绝、超时写入调试日志。
- 审批处置同时写入 AuditLogEntry（操作内容、风险等级、最终处置），供审计查询；F11 的触发规则只进调试日志。
- 审批卡片内容不暴露规则名称、优先级或配置路径等内部信息。

## 数据流

```
操作被 Deny / 命中高风险名单
  │
  ├─ 子 Session / 心跳 / 黑名单 / whitelist 模式 → 静默 Deny 或通知（结束）
  │
  └─ 进入审批
        │
        ▼
     去重检查：同 Agent-User + 同操作 → 直接返回 Deny，不分配 ID、不重复推送
        │
        ▼
     创建审批请求（分配 Session 内递增 ID）
        │
        ▼
     推送 Owner 审批卡片（经 Gateway → IM Adapter 渲染）
        │
        ▼
     Owner 响应（Gateway 硬拦截，不进入 Agent Session）
        │
        ├─ 单次放行 → 注入一次性 Allow → 回调恢复执行
        ├─ 加入白名单 → 写入规则 → 按新规则评估 → 回调
        └─ 拒绝 → 回调返回 Deny
```

关键分支：

- 超时 → 自动返回 Deny，重复申请限制解除。
- 可捕获的关闭流程 → 清空队列，所有等待请求以 Deny 结束；进程崩溃/重启由 Session 恢复机制处理。
- 审批卡片推送经 Gateway/外部层；Owner 的审批指令同样经 Gateway 硬拦截。

## 模块关系

- **上游**：权限引擎（产出 Deny 结果）、Gateway（审批指令拦截）、tools / session / gateway（经 PermissionGate 发起需审批的判定）、沙盒（移出沙盒与文件越界请求）
- **下游**：Gateway（审批卡片推送通道与审批结果回调通道；Agent Session 经 Gateway 接收回调）、IM Adapter（经 Gateway 渲染审批卡片）、Session（恢复执行或返回 Deny）、权限配置管理（白名单规则写入与新用户注册落盘）、沙盒（移出沙盒决策结果）、[common AuditLogger](../common/core-traits.md#auditlogger)（审批处置审计条目）、debug_log（审批生命周期事件）
- **相关**：权限配置管理（新用户注册审批）
- **无关**：LLM Provider（不参与审批）
