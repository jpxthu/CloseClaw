# Debug Log 需求

## 概述

当出现不符合预期的表现时，系统能够完整还原对外部不可见的系统内部行为过程，以便运维 Agent 根据日志和代码定位问题根因。

## 功能需求

### F1. 完整消息链路追踪

每条从 IM 平台到达的消息在整个处理生命周期中携带统一的追踪标识。从平台到达、Processor Chain 处理、路由决策、LLM 调用、工具执行到出站发送，各阶段产生的日志均记录该标识，以便后续串联为一条完整链路。

当 LLM 调用或工具执行触发下游子调用时，子调用的日志与主链路可关联，排查时能纳入同一条链路。

### F2. 分层日志级别

运维 Agent 能按级别过滤日志：
- **异常**：功能不可用或受损，必须人工关注
- **降级告警**：功能降级但可用，需要关注但不紧急
- **关键事件**：消息到达、路由决策、LLM 调用起止、发送完成等生命周期节点
- **中间状态**：Session 查找结果、内容过滤详情、权限检查结果等中间步骤
- **完整内容**：入站原始消息、LLM 完整请求和响应、工具完整参数和返回、出站消息全文

凭据类敏感数据（见 F4）在任何日志级别均不记录明文。

Owner 可通过配置控制记录的最低日志级别，默认记录"中间状态"及以上。日志级别从低到高为：完整内容 → 中间状态 → 关键事件 → 降级告警 → 异常，设置最低级别后将记录该级别及更高级别的事件。

> **交叉引用**：最低日志级别属于日志配置项，变更后自下一条日志起生效；配置重载机制详见 [config §F4](config.md)（配置重载）。

### F3. 日志存储与保留

日志按自然日写入单个文件，每日轮转。超过保留天数的日志文件自动删除。保留天数可由 Owner 配置，变更后自下一次清理起生效。Owner 可手动触发日志清理，删除指定时间范围或全部的日志文件（仅限调试日志框架自身的日志文件，不含各模块已有的日志机制，如 Session 的对话历史 checkpoint 文件）。

日志产生即持久化，不做批量缓冲写入。写入失败不阻塞消息的正常流转。写入失败需作为系统异常记录（见非功能需求）。

### F4. 隐私保护

凭据类敏感数据（API Key、token 等）在任何日志级别均不记录明文，以脱敏标记占位。

### F5. 日志分析与排查

运维 Agent 读取日志文件后，能通过追踪标识串联一条消息的完整链路（因写入失败而缺失的节点除外），结合代码定位问题根因。

### F6. 现有日志机制复用

调试日志框架不替代各模块已有的日志机制（如 Session 的对话历史 checkpoint 文件）。框架沿用 F1 的追踪标识、F2 的分级体系和 F4 的脱敏规则呈现各模块已记录的事件，同一事件不重复写入框架日志。

## 非功能需求

- 每条日志事件包含时间戳，精确度确保事件按发生顺序可还原
- 日志格式对程序和人类均可读——运维 Agent 能直接解析其中的结构化数据
- 日志写入失败需记录为系统异常
