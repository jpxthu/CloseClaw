# IM Adapter 需求

## 概述

IM Adapter 模块满足 CloseClaw 跨消息平台运行的核心诉求——用户和 Agent 可以通过飞书、Discord、Telegram 等多种 IM 平台与 CloseClaw 交互，消息格式在各平台间无缝转换，无需感知底层平台差异。

## 功能需求

### F1. 多平台插件化适配

CloseClaw 需要支持多种 IM 平台，每个平台以独立插件形式接入。新增平台不改变现有平台及核心功能的行为。平台支持可按需启用——默认只启用配置过的平台。

> **交叉引用**：平台启停的生效机制详见 [可扩展性](#可扩展性)（配置变更触发重启）。

每个平台插件负责本平台消息与统一格式的互转，并提供该平台特有的工具能力。

### F2. 入站消息归一化

来自不同 IM 平台的消息在进入系统内部前，需要被归一化为统一的消息形式，使下游模块无需感知平台差异。归一化工作由各平台插件在入站解析时完成。

归一化后的消息包含平台标识、发送者、会话对端、账号标识、消息正文等标准化字段。各平台特有的元数据仅以其取值进入归一化结构，平台特有的字段名不进入归一化结构。

- **平台标识**：消息来源平台
- **发送者**：发消息的用户在该平台上的身份标识；标识的取值按接收方机器人应用隔离，同一用户在同一平台、不同机器人应用语境下的取值不同且不可直接互换
- **会话对端**：消息所属 Session 的上下文锚点，由各平台插件按平台语义确定，其取值粒度随平台形态而定，不设跨平台的统一取值规则。会话对端需满足：同一 Session 内消息的会话对端取值相同；在同一平台、同一发送者、同一账号标识下，不同 Session 的会话对端取值不同。当平台自然锚点不足以区分 Session 时，插件在取值内补充更细粒度的上下文信息。
- **账号标识**：发送者对应的 CloseClaw 用户 ID，经身份映射得到
- **消息正文**：消息的文本内容

**标识与身份 / 会话映射**：一条入站消息的归一化字段共同确定「路由到哪个 Agent、归属哪个 User、进入哪个 Session」。接收消息的机器人应用与发送者是两个独立身份：

- **接收方机器人应用 → Agent**：接收该消息的机器人应用决定消息路由到的 Agent。
- **发送者 → User**：发送者的平台身份标识经身份映射得到 CloseClaw 用户 ID，即账号标识。
- **四项标识 + Agent 范围 → Session**：平台标识、发送者、会话对端、账号标识在 Agent 范围内共同确定主 Agent Session。

各平台特有字段的名称与取值语义由平台子文档定义。

> **交叉引用**：机器人与 Agent 的绑定及消息路由详见 [gateway §F4](gateway.md)（普通消息路由到对话）。
> **交叉引用**：机器人到 Agent 的绑定关系配置详见 [config §F1](config.md)（多文件配置结构）。
> **交叉引用**：User 身份体系与绑定规则详见 [permission §F1](permission.md)（身份体系）。
> **交叉引用**：Session 的确定、查找、创建与恢复详见 [session §F1](session.md)（对话持久化与恢复）。
> **交叉引用**：飞书标识的名称与取值语义详见 [im_adapter/feishu §F1](im_adapter/feishu.md)（飞书入站消息接收）。

引用/回复消息：若平台支持消息引用功能，被引用消息的文本内容需截断后拼接到消息正文前（截断至 500 字符，超出部分以 ... 表示），以引用形式呈现。

> **交叉引用**：非文本消息（图片、文件、音频等）的处理由 Gateway 负责。详见 [gateway §F3](gateway.md)（消息类型识别与非文本处理）。

### F3. 出站消息格式自动选择

Agent 输出消息在发送到 IM 平台前，需根据内容特征自动选择输出格式。默认使用富格式消息；仅当消息内容为纯文本（无任何格式标记、无换行、无 Thinking/Tool 块、无交互指令）时，才使用轻量文本消息。

包含以下任一特征的内容，需使用富格式消息发送：Markdown 格式标记（标题、粗体、斜体、代码块、列表、引用、链接、分割线等）、换行符、Thinking 块、Tool 块、交互指令（平台支持交互元素时渲染为交互控件）。

流式输出的内容使用富格式消息——流式内容在生成完成前无法判定是否为纯文本；轻量文本消息仅用于内容在发送前已完整生成、且判定为纯文本的消息。消息一经发出，其格式不因后续生成的内容而改变。

格式选择由系统自动完成，用户和 Agent 无需手动指定输出格式。

### F4. 流式增量渲染

Agent 流式输出时，消息应逐步渲染并发送到 IM 平台，使用户在 Agent 响应生成过程中即可看到已生成的内容，无需等待完整响应。

文本内容以连贯的片段逐步展示：片段以结构边界（如换行、句末标点）为切分依据、不逐字堆砌；为尽早呈现，结构边界未至时可先行下发已生成内容，不积压至响应结束。代码块以完整块输出，确保语法高亮正确渲染。

Thinking 块和 Tool 块累积完整内容后一次性展示。图片、音频、文件等非文本消息不参与流式渲染，直接交由平台按原生格式渲染。

> **交叉引用**：流式渲染错误的统一降级处理由 Gateway 负责。详见 [gateway §F7](gateway.md)（出站消息统一处理）。
> **交叉引用**：Thinking 块的可见性策略（默认展示范围与按需查看）详见 [llm §F3](llm.md)（推理过程可见与安全）。
> **交叉引用**：代码块高亮规则详见 [F5](#f5-代码块语法高亮)（代码块语法高亮）。

### F5. 代码块语法高亮

消息中的代码块需要按标注的编程语言进行语法高亮渲染，各平台按自身能力提供最佳渲染效果：

- 平台原生支持代码块高亮的，使用平台原生能力实现语法高亮
- 平台原生不支持、但其显示环境具备高亮能力的，通过该环境的显示能力实现语法高亮
- 平台不支持代码块高亮的，以纯文本形式展示代码

各平台支持高亮的语言范围由自身能力决定。

### F6. 渲染与发送分离

Agent 输出先渲染为平台可识别的消息格式，再发送到 IM 平台；渲染与发送是两个相互独立的环节。

> **交叉引用**：渲染与发送之间的拦截检查（审计、频率限制等）由 Gateway 负责。详见 [gateway §F7](gateway.md)（出站消息统一处理）。

### F7. 平台接口真实性验证

IM 平台的接口行为可能随平台侧变更而漂移（事件结构、字段语义、接口可用性等）。为了在不依赖日常运行的情况下及时发现此类变化：

- 除基于已采集真实数据的离线验证外，每个平台还需提供一套使用真实平台账号的验证手段：向平台发起真实的发送与接收，验证接口行为与已采集数据仍一致
- 该验证不进入自动化流程，由 Owner（或平台维护者）不定期手动触发
- 平台凭证与真实身份信息不存储于代码库内

### F8. 调试日志

IM Adapter 模块在以下环节记录调试日志：
- 入站消息解析（平台、消息类型、解析耗时）
- 出站渲染结果（平台、渲染耗时）
- 平台 API 调用发送结果（平台、目标、发送耗时）

> **交叉引用**：完整消息链路追踪详见 [debug_log §F1](debug_log.md)（完整消息链路追踪）。
> **交叉引用**：分层日志级别详见 [debug_log §F2](debug_log.md)（分层日志级别）。
> **交叉引用**：日志存储与保留详见 [debug_log §F3](debug_log.md)（日志存储与保留）。
> **交叉引用**：隐私保护详见 [debug_log §F4](debug_log.md)（隐私保护）。

### F9. 媒体文件收发与存储

> **按 Owner 要求暂不设计**：多媒体（图片、文件、音频等非文本消息）相关需求现阶段不设计，本节内容为暂存草稿、不作为当前需求约束。

IM 平台上的图片、文件等媒体在收发时落盘存储，使媒体内容可被 Agent 使用、且不随平台链接过期而失效。

**入站**：

- 平台插件在接收到含媒体的消息时，立即将媒体下载并存储到统一的媒体存储目录（入站子目录），不依赖平台侧临时链接的有效期
- 归一化消息通过媒体引用字段携带媒体；媒体引用由系统解析为本地媒体文件，下游模块不接触平台侧下载链接与凭证
- 入站媒体保留经安全净化的原始文件名，并附加唯一后缀防止冲突；记录文件大小与 MIME 类型

**Agent 上下文形态**：

- 图片类媒体以图片内容直接进入 LLM 上下文，使 Agent 能直接看图；受模型输入大小限制而无法直接承载的图片以媒体引用进入上下文
- 模型输入大小限制由模型能力决定，非系统配置项，系统不自行设定；是否超限由模型接口报错判断
- 非图片媒体（文件、音频等）以媒体引用进入上下文，Agent 通过引用使用媒体内容
- 上下文的文本表示中只出现媒体引用，不出现本地文件系统路径

**出站**：

- Agent 发送媒体时，待发送的媒体以媒体引用形式表示，Agent 生成的文件以工作区内路径表示（相对路径基于工作区解析）
- 系统仅从工作区目录与媒体存储目录读取待发送的媒体文件；范围外路径拒绝发送并给出清晰提示
- 发出的媒体在媒体存储目录保留副本（出站子目录），供审计与重发

**生命周期**：

- 媒体清理支持两种机制：跟随 Session 生命周期（Session 被清理或不再被任何 Session 引用时，系统清理对应媒体；归档语义及归档与清理的区别详见 [session §F6](session.md)（Session 归档与清理））；以及按固定保留期清理，保留期可配置，默认 7 天。跟随 Session 生命周期的清理机制为可选项；若提供，须以低优先级执行，不影响系统的正常使用
- 清理机制可同时启用，互不依赖

> **交叉引用**：保留期属于媒体配置项，变更后自下一次清理扫描起生效。配置重载机制详见 [config §F4](config.md)（配置重载）。

## 非功能需求

### 可扩展性

- 新增平台或停用已有平台后需重启后方可生效；重启由配置变更自动触发，无需手动操作。详见 [config §F4](config.md)（配置重载）

### 稳定性

- 单个平台插件的初始化失败不影响其他已启用平台的正常运行
- 平台 API 调用失败时，系统正常降级，不导致进程崩溃

### 安全性

- 平台凭证（token 等）由各平台插件自行管理，不在模块间传递
