# 需求文档写作标准

## 定位

需求文档纯粹记录 Owner 的需求、使用场景和日常使用习惯。不讨论技术实现、不涉及架构设计。

**信息来源**：需求文档的信息**只来源于 Owner 本人**，以及与 Owner 一起进行的调研和商讨结论。不得从代码、设计文档或其他来源自行推断需求。

**与设计文档的关系**：设计文档是需求和代码之间的桥梁——将需求翻译为实现层的架构蓝图。设计文档**必须遵从需求文档**，若设计文档的方案与需求文档冲突，以需求文档为准，设计争议提给 Owner 裁决。设计文档的 README 中必须引用对应的需求文档。

## 术语

- **Owner**：项目所有者，唯一的产品决策者
- **User**：CloseClaw 的最终使用者，包括 Owner 与非 Owner User
- **Agent**：AI Agent，系统的另一类使用者（通过工具和 prompt 与系统交互）

**命名约定**：模块名、产品名、技术专有名词保留英文原文，不翻译；正文中的“用户”为 User 的中文泛称。

## 文件组织

```
docs/requirements/
├── README.md              ← 需求文档总索引
├── <模块名>.md            ← 每个模块一个主需求文件
└── <模块名>/              ← 独立平台/插件子文件（可选）
    └── <平台名或插件名>.md
```

规则：
- 一个模块一个主需求文件；模块下可拆独立平台/插件子文件（如 `im_adapter/feishu.md`）
- 模块名与 `docs/design/` 目录对应
- 需求跨模块时，放在归属模块的文件中，其他模块用交叉引用替代

### 交叉引用

需求定义在模块间不重复。当某功能域的需求点已由另一模块完整定义时，引用方在对应功能域末尾标注来源。

**格式**

跨文档引用：`> **交叉引用**：<说明>。详见 [模块名 §Fx](文件名.md)（章节标题）。`

同文档引用省略模块名与文件名，标注沿用上述 `> **交叉引用**` 写法，链接文本改用 `Fx`、链接目标改用本文件的章节锚点：`> **交叉引用**：<说明>。详见 [Fx](#章节锚点)（章节标题）。`

章节锚点取章节标题的 GitHub 锚点形式（转小写、去标点、空格转 `-`），如 `### F9. 工具扩展接入` 对应 `#f9-工具扩展接入`。

每条引用单独一行。引用其他需求文档使用文件名字符串，不用 `../` 相对路径：同目录写 `agent.md`，子目录写 `im_adapter/feishu.md`。

**归属裁定**

同一个需求点在多份需求文档中出现时，以设计文档的模块职责划分为准进行归属裁定（此处仅借设计文档的模块职责划分确定归属文档，不作需求来源）。定义留在归属模块，其他模块用交叉引用替代。归属有争议时提给 Owner。

**引用完整性**

- **必须写交叉引用的情形**：跨模块的行为衔接；本模块消费或产出的数据 / 事件被其他模块使用；被其他模块引用的术语或定义。
- **不得悬空引用**：交叉引用指向的章节必须真实存在且内容匹配；发现悬空引用即修（补定义或改引用）。
- **口径一致**：引用方与被引方的表述必须一致；不一致时以被引方（归属模块）为准，并修订引用方。

## 写作要求

1. **影响用户体验的细节必须写清**：凡会影响 User 可感知结果（回复内容与模型行为、成本、可用性等）的细节，都必须在需求文档中定义清楚，不得以“这属于设计”为由留白。判定标准：该细节若交给开发自行决定，会导致 User 可感知的行为差异——就必须写。
   - 与红线「不写技术实现方案」的边界：影响 User 可感知结果与模型行为的**交互契约**（如对话压缩时送哪些消息、以什么角色、什么顺序、对缓存的影响）属于需求，要写清；纯粹的内部实现结构（数据结构、接口、存储方案）属于设计，不写。
2. **改前先读全貌**：修改任何需求文档前，必须先读 [README.md](README.md)（需求索引）与受影响的相关需求文档，确认定义归属，避免重复定义与平行定义。
3. **术语与计量**：一个词只表达一个概念，禁止一词两义；计量指标必须写明基准（分母）与口径；可配置项必须给出默认值，以及配置项之间的约束关系。
4. **无争议项不是 gap**：审查中遇到“无争议却像 gap”的情况，是文档缺陷信号——通常源于交叉引用缺失或措辞歧义，应据此修文档本身。

## 章节结构

固定 3 节，不增不减。

```
# <模块名> 需求

## 概述
一句话：这个模块要满足用户的什么核心诉求

## 功能需求
按功能域组织，每个功能域一个小节，编号 `### Fx. <名称>`（Fx 为稳定标识符）。
写法：客观陈述，不编故事，角色自然体现在描述中（Owner 可以…… / 非 Owner User 可以…… / Agent 会……），覆盖模块涉及的所有角色视角。

## 非功能需求
性能、可用性、安全性、可观测性等质量属性的用户期望。

性能不写时间/延迟量化指标，改以架构与设计的理论最优性表述（能做 O(1)，不做 O(log n)）。若为平衡架构复杂度与稳定性而放弃理论最优，需由 Owner 明确该取舍是否可接受；即使取舍被接受，需求表述仍不引入时间/延迟量化指标。

可用性、安全性、可观测性等其他质量属性以用户可感知的表述为准，不写技术指标（如“数据库连接池大小”）。
```

## 红线

**不写**：
- 技术实现方案、架构设计、模块接口
- 代码相关内容（函数名、变量名、crate 名、数据结构）
- 设计取舍过程、技术选型讨论
- 现状问题（“当前代码中……”）
- 借鉴来源（“参考 XXX 产品”）
- 未来计划、开发步骤
- 验收标准与优先级标注（Given/When/Then、P0/P1/P2 等——需求文档不是测试计划）
- 第一人称虚构叙事（“作为 X，我想 Y，以便 Z”——这是用户故事，不是需求文档）
- 超出 3 节的额外章节
