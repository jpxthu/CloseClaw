# Permission 需求

## 概述

Owner 需要一套身份型访问控制系统：定义「谁能以什么身份做什么」，覆盖 Agent 工具调用和 User 斜杠指令两大类操作，在操作被拦截时提供可控的审批通道，并以沙盒在操作系统层强制 Agent 的文件访问范围。系统自身行为（Session 管理、消息路由、系统提示构建，以及状态查询、设置等非命令类斜杠指令）不经过权限评估；纳入权限评估的斜杠指令仅为命令类指令（如 `/exec`、`/git`）。

## 功能需求

### F1. 身份体系

Owner 需要系统区分两种独立身份：

- **Agent 身份**：每个 Agent 有独立的权限边界。新建 Agent 默认只能收发消息，无文件读写、命令行、网络访问权限。Agent 的操作始终在某个 User 上下文中执行。
- **User 身份**：每个 User 通过 IM 渠道 + IM 用户标识的组合绑定到系统。新建 User 默认无任何权限，收发消息也需 Owner 显式授予。不区分用户组，所有权限以个人为单位。

User 上下文的来源由场景决定：IM 消息来自发送者，子 Session 继承父 Session 的 User 上下文。

Owner 的 User ID 固定为 `owner`。

> **交叉引用**：CLI 渠道的 User 上下文详见 [cli §F1](cli.md)（终端对话）。
> **交叉引用**：IM 消息的发送者标识等入站归一化字段详见 [im_adapter §F2](im_adapter.md)（入站消息归一化）。
> **交叉引用**：机器人 ↔ Agent、IM 用户 ↔ User 两类双向绑定（含入站/出站方向与基数规则）的权威定义与存储详见 [config §F1](config.md)（多文件配置结构）。
> **交叉引用**：跨平台身份映射在完整消息流中的角色详见 [message_flow §F3](message_flow.md)（跨机器人双接收与身份归并）——建议结合阅读以理解完整产品流程。
> **交叉引用**：消息路由到 Agent 详见 [gateway §F4](gateway.md)（普通消息路由到对话）。
> **交叉引用**：平台、发送者、会话对端、账号四项标识共同确定主 Agent Session 详见 [session §F1](session.md)（对话持久化与恢复）。
> **交叉引用**：平台身份标识按接收方应用语境取值、跨应用隔离（如飞书 open_id）详见 [im_adapter/feishu §F1](im_adapter/feishu.md)（飞书入站消息接收）。

### F2. 权限维度

Owner 需要八个独立管理的权限维度。

读与写共用同一套文件级权限评估机制。各权限维度的白名单指该维度的持久允许规则；命令行维度的白名单是「可在宿主执行的命令」集合。

- **读**：控制 Agent 可读取的文件和目录范围；范围由沙盒以操作系统级强制（见 F12，`always allow` 模式除外）。
- **写**：控制 Agent 可写入的文件和目录范围；范围由沙盒以操作系统级强制（见 F12，`always allow` 模式除外）。
- **命令行**：控制 Agent 可执行的命令，白名单与黑名单并存（记录粒度见 F12，不得加入白名单的命令见 F7），同一命令同时列入两表时黑名单优先。命令按以下顺序处理：
  1. 黑名单内的命令无论沙盒内外均不允许执行，也不进入审批流程。
  2. 命中白名单的命令在宿主执行；涉及受保护路径时按高风险操作处置，需 Owner 单次确认（见 F7）。
  3. 未命中白名单的命令在 `whitelist` 模式下直接拒绝。
  4. 未命中白名单的命令在 `sandbox` 与 `always allow` 模式下先做结构解析；解析无法确定时视为可疑、进入审批（见 [tools §F8](tools.md)（命令安全防护）），解析确定后按沙盒模式执行。
- **工具调用**：控制 Agent 能否调用某个工具。仅符合工具调用格式的 LLM 输出会进入工具模块（格式解析先于权限评估）；Agent 通过工具进行的文件读写由读/写维度评估，本维度不重复评估。
- **收发消息**：控制 User 与 Agent（LLM）之间的消息往来——User 消息送入 LLM，以及 LLM 和工具发往 User 的消息；该维度与渠道（IM 或 CLI）无关，对所有渠道一致生效。
- **网络访问**：控制 Agent 可访问的网络资源。沙盒内默认拒绝所有网络访问（见 F12）。在宿主执行的命令不受本维度限制。工具访问网络按域名授权，未授权的域名一律拒绝。
- **跨 Agent 通信**：控制 Agent 之间能否通信（spawn、消息传递等）。默认拒绝。
- **配置写入**：控制 Agent 能否写入系统配置文件（权限配置文件另受 Owner 独占约束，见 F4）。默认拒绝，且该维度下的操作一律为高风险——只能单次放行，不能被加入白名单。

### F12. 沙盒

Owner 需要 Agent 的文件访问范围以**操作系统级强制**落地，而非仅靠路径规则匹配——Agent 可能编写脚本反复拼接路径，规则难以穷尽；沙盒在操作系统层拦截越界访问，路径如何拼装都无法绕过。

#### 强制范围

沙盒启用时，强制约束三类访问：

- Agent 的文件读写工具访问（read/write/edit）
- 命令行中在沙盒内执行的进程（含其调用的脚本与子进程）
- 沙盒内进程的网络访问：默认拒绝所有网络访问

#### 边界来源

边界来自读/写维度配置的路径范围（见 F2）：

- 可读范围 = 可写范围 ∪ 读维度配置的路径范围（写入必然伴随读取）。这里只定义沙盒强制的范围，读取权限仍按读维度规则评估。
- 工作目录（见 F3）自动纳入可读写范围。

#### 沙盒模式

沙盒模式由权限规则定义，按 Agent 侧配置，User 侧不覆写；默认 `sandbox`。共三种模式：

- `sandbox`（默认）：白名单命令在宿主执行，不受沙盒范围强制；其余命令与脚本在沙盒内执行，受范围强制。
- `whitelist`：仅白名单命令在宿主执行，不受沙盒范围强制；其余命令一律拒绝。文件读写工具仍受沙盒范围强制。高风险命令不得加入白名单，因此在该模式下无法执行。
- `always allow`：不启用沙盒，命令与文件访问不受范围强制（高风险模式，默认关闭）。

三种模式下黑名单命令一律拒绝；`sandbox` 与 `always allow` 模式下，解析无法确定的命令仍进入审批（见 F2）。

#### 移出沙盒执行

仅 `sandbox` 模式适用，且不适用于黑名单命令。部分命令无法在沙盒内完成（如需网络访问或交互式登录），Agent 可请求将某条命令移出沙盒、在宿主执行；请求进入审批流程（见 F5）。

Owner 对移出请求的处置：单次放行（仅本次，不持久化）、加入白名单（持久，写入权限配置，见 F6）或拒绝。高风险操作不可加入白名单（见 F7）。

命令行维度的白名单按「可执行文件 + 参数前缀」记录；不得加入白名单的命令见 F7。Owner 可随时撤销白名单条目；每次白名单命令的执行都记入调试日志（见 F11）。

#### 不降级

沙盒无法启用时，受沙盒约束的操作一律拒绝执行，不降级为无约束执行。

#### 沙盒引擎

沙盒引擎采用操作系统原生隔离机制、按平台选择：Linux 以 bubblewrap 为主、内核 Landlock 兜底（WSL2 按 Linux 平台处理），macOS 以 Seatbelt 实现。选用操作系统原生机制的原因：用户无需安装容器运行时，进程级开销小，且不引入宿主与沙盒之间的文件挂载点。

> **交叉引用**：沙盒移出请求的审批入队、推送与回调详见 [F5](#f5-审批工作流)（审批工作流）。

### F3. 权限决策模型

Owner 需要 Agent 侧与 User 侧的规则交集决策：操作只有在双方都允许时才放行，任一方拒绝即拒绝。

每项操作各由一个权限维度作出授权决定，其余权限维度只能否决、不能放行。工具调用与其内部的命令执行、文件读写、网络访问分别判定。

作为上述交集决策的例外，每个 User 与 Agent 的组合自动获得其专属工作目录（`{配置目录}/workspaces/{Agent ID}/{User ID}/`）的读写权限。此路径由系统自动创建和管理，Agent 即使权限规则未覆盖此路径也可正常读写；此强制授权不受任何 Deny 规则影响（含沿 spawn 链路传播的 Deny）。

该路径允许 User 直接访问，属影响用户体验的约定，故在需求文档中固定。

权限评估不沿用历史结果：Agent 的每次操作都按当前生效规则重新评估，不缓存评估结论。规则变更即时生效以此机制为前提，热加载详见 F6。

> **交叉引用**：配置目录的操作系统标准位置详见 [platform §F2](platform.md)（操作系统标准配置目录）。

### F4. Owner 特权

Owner 在权限决策中享有以下特权：

- **User 侧豁免**：Owner 作为调用方时，跳过所有 User 侧规则，仅评估 Agent 侧规则。这意味着 Owner 不会被 User 侧规则拦截，只受该 Agent 自身能力边界的限制。
- **权限配置独占**：权限配置文件仅 Owner 可直接写入。Agent 对权限配置文件的读写默认拒绝：写入归配置写入维度，读取归读维度，均属高风险操作，仅经 Owner 单次放行方可执行，不可加入白名单。
- **审批独占**：所有审批请求只推送给 Owner，非 Owner 用户没有审批权力；Owner 的审批决策（单次放行 / 加入白名单 / 拒绝）见 F5。
- **命令执行豁免**：Owner 通过斜杠指令执行的命令类操作（`/exec`、`/git` 等）默认放行，不进入审批流程，也不受沙盒约束；被列入黑名单的命令除外（黑名单对 Owner 同样生效，一律拒绝、不进入审批）。

Owner 其他经权限评估被拦截的操作仍进入审批（见 F5）；非命令类斜杠指令（含审批指令 `/approve-once`、`/approve-whitelist`、`/deny`）不进入权限评估（见概述），审批通道始终可被 Owner 使用。

> **交叉引用**：命令类斜杠指令的行为详见 [slash §F7](slash.md)（工作目录操作）与 [slash §F8](slash.md)（命令执行）。

### F5. 审批工作流

当 Agent 操作被权限系统拒绝时，Owner 不希望直接阻断——需要一个可控的审批通道。

#### 审批触发

权限评估未放行的操作按场景分流处理，以下顺序即匹配优先级，命中即停止：

- 子 Session 场景：直接拒绝，不创建审批请求、不进入审批流程（见 F9）。
- 未注册用户发起的操作：不响应、不创建审批请求（见 F6）。
- 黑名单命令：直接拒绝，不创建审批请求（见 F2）。
- `whitelist` 模式下白名单外命令：直接拒绝，不创建审批请求（见 F12）。
- `sandbox` 与 `always allow` 模式下命令结构解析无法确定：进入审批（见 [tools §F8](tools.md)（命令安全防护））。
- `sandbox` 模式下 Agent 发起的「移出沙盒执行」请求：进入审批（见 F12）。
- 其余场景：自动创建审批请求并推送给 Owner。

沙盒在操作系统层拦截的越界访问不进入审批，直接以执行失败返回。

#### 审批标识

每条审批请求有一个全局唯一的 ID，所有 Agent、所有 Session 共用同一 ID 空间，不同请求的 ID 不会重复。系统同时为每条请求生成一个全局唯一、便于输入的短码，供 Owner 在审批指令中指代目标请求。

不同请求之间不合并：即使操作类型与参数完全相同，也各自对应独立的审批请求与 ID。

#### 审批卡片内容

推送的审批卡片需包含：

- 发起操作的 Agent ID
- 当前 User ID
- 操作类型和参数
- 是否为高风险操作
- 审批短码

#### Owner 决策

Owner 可对审批请求做出三种决策：单次放行（仅本次操作，不持久化）、加入白名单（在该操作所属的权限维度写入持久化允许规则）、拒绝。高风险操作只有单次放行与拒绝两项可选（见 F7）。Owner 通过审批指令表达决策。

按调用方身份区分：

- Owner 审批非 Owner 调用方的操作时：可选择把放行规则写入拒绝的那一侧（Agent 侧或 User 侧），或两侧都写入。
- Owner 自身调用被拦截时：仅评估 Agent 侧（User 侧已豁免）。

#### 等待机制

审批不设等待上限，直到 Owner 作出决策。

等待只作用于发起该操作的那一次工具调用：同一轮中的其他工具调用照常执行并返回结果，不因一条审批未决而整体停摆。

Owner 作出决策后，系统自动向对应 Agent 回调结果，被放行的调用继续执行。

系统异常中断时清空所有等待中的审批请求，并向对应 Agent 返回拒绝信息，避免调用方挂起。

> **交叉引用**：审批指令的语法和 Immediate 标记详见 [slash §F13](slash.md)（审批指令）。

### F6. 权限配置管理

Owner 需要灵活高效地管理权限规则：

- **修改方式**：Owner 通过两种方式修改权限规则：斜杠指令，或审批时选择加入白名单（写入 Agent 侧或 User 侧规则）。两种方式均由系统直接处理，不在 Agent 会话流程内执行。任何修改操作在执行前验证调用方是否为 Owner。
- **热加载**：权限规则变更后即时生效，无需重启 Agent 或系统。下一次权限评估即使用新规则。
- **加载容错**：权限配置文件损坏、缺失或无法加载时不阻塞 Agent 加载，CloseClaw 照常启动，并优先保留其他可用配置。仅当无任何可用配置时，Agent 退化为系统默认权限（仅收发消息），系统明确通知 Owner。
- **新建 User**：User 由 Owner 在权限配置中直接添加，不存在自助注册与注册审批。未注册用户通过 IM 私聊发送的消息不产生任何响应，也不产生注册请求。新建 User 默认无任何权限，包括不能与任何 Agent 通信；Owner 授予权限后，用户才能开始交互。
- **授权粒度**：Owner 分别配置 Agent 侧与 User 侧规则。
  - Agent 侧规则以 Agent 为单位，对该 Agent 的所有调用方生效。
  - User 侧规则以 User 与 Agent 的组合为单位。
  - 两侧各自独立配置八个权限维度，未配置的维度按拒绝处理。

> **交叉引用**：权限配置文件的备份恢复机制详见 [config §F3](config.md)（启动容错与备份恢复）。
> **交叉引用**：权限配置的重载与生效机制详见 [config §F4](config.md)（配置重载）。

### F7. 高风险操作管控

对 Agent 发起的操作，Owner 需要系统对高风险操作施加额外限制：

- 高风险操作永远只能单次放行，不能被加入白名单；任何一次批准都不持久化。
- 高风险操作的审批卡片不显示「加入白名单」选项。
- 高风险判定先于白名单匹配：即使命令已在白名单中，涉及受保护路径的操作仍需 Owner 单次确认。
- 受保护路径至少包含：版本控制目录、权限配置文件、系统配置文件、凭据文件。
- 高风险命令不得加入白名单，单次执行本身不做额外拦截，可作用范围由命令在宿主还是沙盒内执行决定。
- 高风险命令至少包含：`rm`、`dd`、`mkfs`、`chmod`、`chown`、`sudo`、脚本解释器。其中脚本解释器与特权类命令不可加入白名单——持久放行会让沙盒约束失效。

### F8. 安全边界

Owner 需要以下安全保障：

- **配置保护**：权限配置文件的读写永不因白名单机制或工作目录强制授权而放宽。
- **系统设计约束**：权限系统在安全设计上不支持下列操作：禁用 Owner 身份校验、绕过权限系统。
- **工作目录安全**：Agent ID 和 User ID 不得导致越权访问其专属工作目录之外的位置。
- **工作目录并发创建**：并发创建工作目录时不得相互干扰或失败。
- **最小信息原则**：Agent 被拒绝时只收到被拒绝的权限维度（如命令行、写、网络访问），不暴露规则名称、优先级、配置路径；拒绝信息中也不说明该拒绝是否由 Owner 的审批决策产生。

### F9. 子 Session 权限继承

Owner 需要子 Session 的权限不超出父 Agent：

- 父 Agent 派生子 Session 时，子 Session 的实际权限 = 目标 Agent 配置权限 ∩ 父 Session 实际权限 ∩ 继承的 User 侧规则。
- 权限沿 spawn 链路只能变窄，不能变宽。
- 链路中所有父 Agent 的 Deny 规则沿链路向子 Session 传播——每增加一级深度，Deny 规则只增不减。
- 子 Session 的权限评估除交集计算外，还需额外检查父 Agent 传入的 Deny 规则。
- 子 Session 需要审批的操作直接拒绝，不创建审批请求、不通知 Owner；子 Session 不与 User 交互。收发消息维度对子 Session 恒为拒绝，子 Session 只与父 Session 通信。
- 派生控制项的默认值（配置项见 [agent §F9](agent.md)（子 Session 创建控制））：
  - 目标范围：只能派生同一 Agent 的子 Session。
  - 层级深度上限：1。
  - 并发上限：同一父 Agent 下同时存活的子 Session 数量上限为 2。

### F11. 调试日志

权限系统在以下环节记录调试日志：

- 权限评估结果（放行/拒绝，含触发的规则）
- 审批请求的完整生命周期（创建、推送通知、单次放行、加入白名单、拒绝）
- 权限规则变更
- 白名单条目的新增、撤销与每次使用

## 非功能需求

- 权限评估不构成 Agent 操作的可感知瓶颈：每次操作都重新评估、不缓存结论（见 F3），开销不随 Session 数量、Agent 数量、历史审批记录或运行时长增长，仅与当前生效规则集及 spawn 链路深度相关。
- 产生审批请求时，审批卡片立即推送到 Owner 的 IM 渠道，不因系统内部处理引入 Owner 可感知的延迟。
- 系统应在无 Owner 在线时保持可用——等待中的审批请求不应阻塞系统其他功能。
