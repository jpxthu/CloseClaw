# Permission 需求

## 概述

Owner 需要一套身份型访问控制系统：定义「谁能以什么身份做什么」，覆盖 Agent 工具调用和用户斜杠指令两大类操作，在操作被拦截时提供可控的审批通道，并以沙盒在操作系统层强制 Agent 的文件访问范围。系统自身行为（Session 管理、消息路由、系统提示构建，以及状态查询、设置等非命令类斜杠指令）不经过权限评估；纳入权限评估的斜杠指令仅为命令类指令（如 `/exec`、`/git`）。

## 功能需求

### F1. 身份体系

Owner 需要系统区分两种独立身份：

- **Agent 身份**：每个 Agent 有独立的权限边界。新建 Agent 默认具备：收发消息、在沙盒内执行不在白名单也不在黑名单的命令（见 F2、F12）、按自身配置档案的工具白名单调用工具（见 [agent §F1](agent.md)（Agent 配置档案））。其余维度默认拒绝：宿主命令（白名单为空）、网络访问、跨 Agent 通信、配置写入；这些拒绝仍可按 F5 进入审批（黑名单命令、子 Session、心跳、沙盒不可用等场景除外）。其专属 workspace 的读写按 F3 自动放行，不依赖权限规则。Agent 的操作始终在某个 User 上下文中执行。
- **User 身份**：每个 User 通过 IM 渠道 + IM User ID 的组合绑定到系统。一个 User 可以绑定多个 IM 渠道（如飞书、Telegram），各渠道的用户标识映射为同一个人。新建 User 默认无任何权限，收发消息也需 Owner 显式授予（workspace 自动授权见 F3，在无收发消息权限时不构成可交互能力）。不区分用户组，所有权限以个人为单位。

初始 Agent `master` 是上述默认权限的例外：八个权限维度全部开放（黑名单命令与高风险操作名单对 `master` 同样生效）、沙盒默认不启用（见 F12；该基线属高风险模式）。权限配置文件对任何 Agent（含 `master`）一律不可读写（见 F4）。

User 上下文的来源由场景决定：IM 消息来自发送者、心跳（Heartbeat）使用任务配置中指定的 User ID、子 Session 继承父 Session 的 User 上下文。

> **交叉引用**：CLI 渠道的 User 上下文详见 [cli §F1](cli.md)（终端对话）。
> **交叉引用**：IM 消息的发送者标识等入站归一化字段详见 [im_adapter §F2](im_adapter.md)（入站消息归一化）。
> **交叉引用**：机器人 ↔ Agent、IM 用户 ↔ User 两类双向绑定（含入站/出站方向与基数规则）的权威定义与存储详见 [config §F1](config.md)（多文件配置结构）。
> **交叉引用**：跨机器人（跨应用语境）身份归并与标识隔离在完整消息流中的角色详见 [message_flow §F3](message_flow.md)（跨机器人身份归并）——建议结合阅读以理解完整产品流程。
> **交叉引用**：消息路由到 Agent 详见 [gateway §F4](gateway.md)（普通消息路由到对话）。
> **交叉引用**：平台、发送者、会话对端、账号四项标识共同确定主 Agent Session 详见 [session §F1](session.md)（对话持久化与恢复）。
> **交叉引用**：平台身份标识按接收方应用语境取值、跨应用隔离（如飞书 open_id）详见 [im_adapter/feishu §F1](im_adapter/feishu.md)（飞书入站消息接收）。
> **交叉引用**：初始 Agent 的创建与默认工具范围详见 [agent §F5](agent.md)（初始 Agent 创建）、[agent §F1](agent.md)（Agent 配置档案）。

Owner 的 User ID 固定为 `owner`。

### F2. 权限维度

Owner 需要八个独立管理的权限维度：

- **读**：控制 Agent 可读取的文件和目录范围；范围由沙盒以操作系统级强制（见 F12，放行模式的 Agent 除外）。可写范围自动并入可读范围。
- **写**：控制 Agent 可写入的文件和目录范围；范围由沙盒以操作系统级强制（见 F12，放行模式的 Agent 除外）。写权限包含读权限，读权限不包含写权限。
- **命令行**：控制 Agent 可执行的命令。黑名单与白名单并存，同一命令同时列入两表时黑名单优先。处理顺序：
  1. 黑名单内的命令在沙盒内外一律不允许执行，也不进入审批。
  2. 白名单内的命令在沙盒内外均允许执行。
  3. 其余命令在沙盒内允许执行。

  命令的默认执行位置由沙盒模式决定，单次调用可用可选参数指定（见 F12）。白名单即「可在沙盒外执行的命令集合」，白名单命令在沙盒外执行无需审批；非白名单命令请求在沙盒外执行时进入审批（默认模式；严格模式直接拒绝、放行模式无需审批，见 F12）。解释器类命令不得加入白名单，否则沙盒约束失效。上述处理顺序是默认模式的口径，严格模式与放行模式下的差异见 F12。
- **工具调用**：控制 Agent 能否调用某个工具。仅符合工具调用格式的 LLM 输出会进入工具模块（格式解析先于权限评估）；Agent 通过工具进行的文件读写由读/写维度评估，本维度不重复评估。工具范围的权威定义（白名单/黑名单）在 Agent 配置档案中（见 agent §F1），本维度决定该范围是否对当前 Agent 生效。
- **收发消息**：控制 User 与 Agent（LLM）之间的消息往来——User 消息送入 LLM，以及 LLM 和工具发往 User 的消息；该维度与渠道（IM 或 CLI）无关，对所有渠道一致生效。
- **网络访问**：控制 Agent 可访问的网络资源（主机、端口）。默认拒绝所有网络访问。沙盒内的命令无法访问网络，网络访问只发生在沙盒外执行的命令中，因此该维度在沙盒外执行请求的审批中一并判定（见 F12）。
- **跨 Agent 通信**：控制 Agent 之间能否通信（spawn、消息传递等）。默认拒绝。
- **配置写入**：控制 Agent 能否写入 CloseClaw 的系统配置文件（Agent 配置、渠道与账户绑定、Gateway 参数等）。默认拒绝，且该维度下的操作属高风险（见 F7）——只能单次放行，不能被加入白名单。权限配置文件不在本维度范围内：该文件对任何 Agent 一律不可读写（见 F4）。

### F12. 沙盒

Owner 需要 Agent 的文件访问范围以**操作系统级强制**落地，而非仅靠路径规则匹配——Agent 可能编写脚本反复拼接路径，规则难以穷尽；沙盒在操作系统层拦截越界访问，路径如何拼装都无法绕过。

#### 强制范围

沙盒启用时，强制约束两类访问（均为 Agent 发起的操作；Owner 与 User 的斜杠指令由系统执行，不经过沙盒）：

- Agent 的文件操作类工具访问（读取、写入、编辑、目录列举、内容搜索等）
- 命令行中在沙盒内执行的进程（含其调用的脚本与子进程）

#### 边界来源

边界来自读/写维度配置的路径范围（见 F2）：

- 可读范围 = 可写范围 ∪ 读维度配置的路径范围（写入必然伴随读取）。
- workspace 路径（见 F3）自动纳入可读写范围。

#### 沙盒模式

沙盒模式由权限规则定义，按 Agent 维度配置，User 维度不覆写。共三种模式（同一命令同时列入白名单与黑名单时黑名单优先，见 F2）：

- **默认模式**（默认）：白名单命令在沙盒内外均允许执行；其余命令在沙盒内执行，受范围强制；黑名单命令一律拒绝。
- **严格模式**：仅白名单命令在沙盒内外允许执行，其余命令一律拒绝（含黑名单命令，见 F2）。
- **放行模式**：不启用沙盒，命令与文件访问不受范围强制（高风险模式，除初始 Agent 的基线外默认关闭）；黑名单命令仍一律拒绝（见 F2）。

#### 执行位置

执行位置是命令调用上的可选参数；缺省位置由沙盒模式决定——默认模式与严格模式在沙盒内，放行模式在沙盒外。部分命令无法在沙盒内完成（如需网络访问或交互式登录），Agent 可对非白名单命令的单次调用指定在沙盒外（宿主）执行，并附上用途说明；该请求进入审批流程（见 F5）。

Owner 对沙盒外执行请求的处置：单次放行（仅本次，不持久化）、加入白名单（持久，写入权限配置，见 F6）或拒绝。执行位置对命令权限的影响已由 F2 定义，本节不重复。

#### 不降级

沙盒无法启用时，受沙盒约束的操作一律拒绝执行，不降级为无约束执行，也不进入审批。

#### 沙盒引擎

沙盒引擎采用操作系统原生隔离机制、按平台选择：Linux 以 bubblewrap 为主、内核 Landlock 兜底（WSL2 归 Linux），macOS 以 Seatbelt 实现。选用操作系统原生机制的原因：用户无需安装容器运行时，进程级开销小，且不引入宿主与沙盒之间的文件挂载边界。

> **交叉引用**：沙盒外执行请求的审批入队、投递与回调详见 [F5](#f5-审批工作流)（审批工作流）。

### F3. 权限决策模型

Owner 需要 Agent 维度和 User 维度的交集决策：操作只有在双方都允许时才放行，任一方拒绝即拒绝。

决策顺序：

1. 命中高风险操作名单的操作（见 F7）只能单次放行，不经其它任何放行路径（Owner 的命令执行豁免见 F4）。
2. 未命中时，Agent-User 组合对其专属 workspace 路径（`{数据根目录}/workspaces/{Agent ID}/{User ID}/`）的读写自动放行。此路径由系统自动创建和管理，Agent 即使权限规则未覆盖此路径也可正常读写；此强制授权不受任何 Deny 规则影响（含沿 spawn 链路传播的 Deny）。
3. 其余操作按 Agent 维度与 User 维度的交集决策。

权限评估不沿用历史结果：Agent 的每次操作都按当前生效规则重新评估，不缓存评估结论。规则变更即时生效以此机制为前提，热加载详见 F6。

### F4. Owner 特权

Owner 在权限决策中享有以下特权：

- **User 维度豁免**：Owner 作为调用方时，跳过所有 User 维度规则，仅评估 Agent 维度。这意味着 Owner 不会被 User 规则拦截，只受该 Agent 自身能力边界的限制。
- **权限配置独占**：权限规则仅 Owner 可通过权限指令与审批加入白名单修改（见 F6）。权限配置文件对任何 Agent（含 `master`）一律不可读写，不进入审批，也不存在放行路径。
- **审批独占**：所有审批请求只推送给 Owner，非 Owner 用户没有审批权力；Owner 的审批决策（单次放行 / 加入白名单 / 拒绝）见 F5。
- **命令执行豁免**：Owner 通过斜杠指令执行的命令类操作（`/exec`、`/git` 等）默认放行，不进入审批流程，也不受沙盒约束；被列入黑名单的命令除外（黑名单对 Owner 同样生效，一律拒绝、不进入审批）。`/exec` 仅 Owner 可用（见 slash §F8）。

Owner 其它经权限评估被拦截的操作仍进入审批（见 F5）；非命令类斜杠指令（含审批指令 `/approve-once`、`/approve-whitelist`、`/deny` 与权限指令 `/perm`）不进入权限评估（见概述），审批通道始终可被 Owner 使用。心跳等无直接用户交互场景的降级处理见 F10。

### F5. 审批工作流

当 Agent 操作被权限系统拒绝时，Owner 不希望直接阻断——需要一个可控的审批通道。

#### 审批触发

操作被拒绝时按场景分流处理：

- 黑名单命令：直接拒绝，不进入审批（见 F2）。
- 沙盒无法启用：直接拒绝，不进入审批（见 F12）。
- 严格模式下白名单外的命令：直接拒绝，不进入审批（见 F12）——包括请求在沙盒外执行的这类命令。
- 子 Session 场景：静默返回拒绝结果，不触发审批（见 F9）。
- 心跳的拒绝：按任务配置处理——静默跳过 / 通知 Owner（见 F10）。
- 非白名单命令请求在沙盒外执行（仅默认模式；放行模式下命令缺省即在沙盒外、无需审批）：进入审批（见 F12）。
- 工具安全防护发起的安全审批（见 tools §F8）：进入同一审批通道。
- 其余场景（其它权限维度拒绝操作）：自动创建审批请求并推送给 Owner。

#### 去重

同一个 Agent-User 组合下、操作类型与参数相同的重复申请直接拒绝，不重复推送审批。

#### 审批卡片内容

推送的审批卡片需包含：

- 发起操作的 Agent ID
- 当前 User ID
- 操作类型和参数
- 风险等级提示
- 审批单号
- 审批指令的用法提示（含单号与维度参数的写法）

命令类操作另附 Agent 提供的命令用途说明。

审批单号全局唯一，跨会话与跨渠道连续自增，不按会话重新计数。

> **交叉引用**：命令用途说明的生成与要求详见 [tools §F8](tools.md)（命令安全防护）。

#### 投递

审批请求推送到 Owner 最近使用的 IM 平台；多平台按最近使用顺序回退，全部投递失败时记录日志（见 gateway §F7）。Owner 在任意会话发出的审批指令均按审批单号命中对应请求，与发出指令的会话无关。CLI 终端会话中存在等待中的审批请求时，终端输出审批提示，Owner 可在终端内直接审批（见 cli §F1）。

#### Owner 决策

Owner 可对审批请求做出三种决策：单次放行（仅本次操作，不持久化）、加入白名单（写入持久化规则）、拒绝。Owner 通过审批指令表达决策——双路径（审批卡片或审批指令）均走同一审批处理逻辑，指令语法见 [slash §F13](slash.md)（审批指令）。

按调用方身份区分：

- Owner 审批非 Owner 调用方的操作时：可按 Agent 维度和 User 维度分别决策（单次放行与加入白名单均适用）——例如仅放行触发操作的 Agent、仅放行当前 User 上下文、或两者均放行。
- Owner 自身调用被拦截时：仅评估 Agent 维度（User 维度已豁免）。

命令类操作只涉及 Agent 维度：命令白名单属于 Agent 维度资产，命令的审批不提供 User 维度放行。

#### 等待机制

Agent 一轮调用多个工具时，有权限的工具可先执行；被拒绝的工具调用进入等待状态，等待 Owner 审批。

审批请求默认等待 5 分钟，超时未响应则自动向 Agent 返回拒绝信息；超时后 Owner 再发审批指令，系统返回错误提示「该审批已超时」。等待时长是权限模块的全局配置项，在配置文件中修改后即时生效、变更后发出的下一个审批请求即使用新值（见 [config §F4](config.md)（配置重载）），不提供运行时指令。Owner 审批完成后系统自动向对应 Agent 回调通知结果。

审批完成或超时后，该操作的重复申请限制解除（去重不再生效），Agent 可重新发起。

系统异常中断时清空所有等待中的审批请求，并向对应 Agent 返回拒绝信息，避免调用方挂起。

> **交叉引用**：审批指令的语法和 Immediate 标记详见 [slash §F13](slash.md)（审批指令）。

### F6. 权限配置管理

Owner 需要灵活高效地管理权限规则：

- **规则构成**：一条权限规则由规则主体（Agent 或 User）、作用维度、生效对象、决策结果（允许 / 拒绝）四项构成。各维度的生效对象形态：读、写为文件系统路径；命令行为命令名；工具调用为工具名；网络访问为主机与端口；收发消息、跨 Agent 通信、配置写入三个维度不细分对象，规则直接作用于该维度。命令行与工具调用两个维度只能以 Agent 为规则主体——命令执行不作为 User 维度的权限项（User 可用的命令类斜杠指令仅 `/git`，按 Agent 维度规则评估，见 slash §F7），工具范围由 Agent 配置档案定义（见 agent §F1）。命令行的允许规则即该 Agent 命令白名单的条目（见 F2）；高风险操作名单内的对象不能被允许规则放行（见 F7）。规则的存储位置、文件格式与语法属实现细节（由设计文档定义）；需求层约束是必须能完整表达上述四项要素。
- **修改方式**：Owner 通过权限指令（列出、新增、删除规则，见 slash §F16）或审批时加入白名单修改权限规则。两种方式均由系统直接处理，不在 Agent 会话流程内执行。任何修改操作在执行前验证调用方是否为 Owner。
- **热加载**：权限规则变更后即时生效，无需重启 Agent 或系统。下一次权限评估即使用新规则。
- **加载容错**：权限配置文件损坏、缺失或无法加载时，不阻塞 Agent 加载，CloseClaw 照常启动，且优先保留其他可用配置。仅当无任何可用配置时，Agent 退化为系统默认权限（见 F1），并明确通知 Owner——初始 Agent 的例外同样依赖其权限配置，退化后不再享有。
- **新建 User**：新建非 Owner 用户需 Owner 审批。新建 User 默认无任何权限，包括不能与任何 Agent 通信。创建后 Owner 需另行授予权限，用户才能开始交互。

> **交叉引用**：权限配置文件的备份恢复机制详见 [config §F3](config.md)（启动容错与备份恢复）。
> **交叉引用**：权限配置的重载与生效机制详见 [config §F4](config.md)（配置重载）。

### F7. 高风险操作管控

Owner 需要系统对高风险操作施加额外限制：

- 高风险操作永远只能单次放行，不能被加入白名单。
- 高风险操作的审批卡片不显示「加入白名单」选项。
- 名单按路径命中，作用于 Agent 对名单内路径的文件读写操作；命令对同一路径的访问按命令行维度评估（见 F2）。
- 名单由系统预定义，当前包含：版本控制目录（`.git`）的读写。名单可按需增补；配置写入维度下的操作天然属高风险（见 F2）。

### F8. 安全边界

Owner 需要以下安全保障：

- **配置保护**：权限配置文件对 Agent 一律不可读写，不受规则、白名单机制或 workspace 强制授权影响（见 F4）。
- **系统设计约束**：权限系统在安全设计上不支持下列操作：禁用 Owner 身份校验、绕过权限系统。
- **workspace 路径安全**：Agent ID 和 User ID 不得导致越权访问其专属 workspace 之外的位置。
- **workspace 并发创建**：并发创建 workspace 目录时不得相互干扰或失败。
- **最小信息原则**：Agent 被拒绝时仅收到操作被拒绝的结果，不暴露规则名称、优先级或配置路径等内部信息。

### F9. 子 Session 权限继承

Owner 需要子 Session 的权限不超出父 Agent：

- 父 Agent 派生子 Session 时，子 Session 的实际权限 = 目标 Agent 配置权限 ∩ 父 Session 实际权限 ∩ 继承的 User 上下文权限。
- 权限沿 spawn 链路只能变窄，不能变宽。
- 链路中所有父 Agent 的 Deny 规则沿链路向子 Session 传播——每增加一级深度，Deny 约束只增不减。
- 子 Session 的权限评估除交集计算外，还需额外检查父 Agent 传入的 Deny 约束。
- workspace 强制授权（见 F3）不参与上述交集——子 Session 同样自动获得其专属 workspace 的读写。
- 子 Session 被拒绝时静默返回拒绝结果，不触发审批流程。

### F10. 无直接用户交互场景的降级处理

Owner 需要对心跳等无直接用户交互的场景做权限降级处理：

- 心跳必须在任务配置中指定一个 User ID；该 User ID 若未注册，则跳过任务并通知 Owner。
- 心跳的操作被拒绝时按配置处理：静默跳过或通知 Owner（心跳无消息通道上下文，不支持进入审批）。
- 心跳日志始终写入调试日志（见 F11），供 Owner 事后查询。

### F11. 调试日志

权限系统在以下环节记录调试日志：
- 权限评估结果（放行/拒绝，含触发的规则）
- 审批请求的完整生命周期（创建、投递、单次放行、加入白名单、拒绝、超时）
- 权限规则变更
- 心跳相关的权限决策与处置（拒绝 / 静默跳过 / 通知 Owner）

> **交叉引用**：日志链路追踪详见 [debug_log §F1](debug_log.md)（完整消息链路追踪）。
> **交叉引用**：分层日志级别详见 [debug_log §F2](debug_log.md)（分层日志级别）。
> **交叉引用**：日志存储与保留详见 [debug_log §F3](debug_log.md)（日志存储与保留）。
> **交叉引用**：隐私保护详见 [debug_log §F4](debug_log.md)（隐私保护）。

## 非功能需求

- 权限评估不构成 Agent 操作的可感知瓶颈：每次操作都重新评估、不缓存结论（见 F3），开销不随 Session 数量、Agent 数量、历史审批记录或运行时长增长，仅与当前生效规则集相关。
- 审批卡片在操作被拒绝后立即推送到 Owner 最近使用的 IM 平台，不因系统内部处理或平台回退引入 Owner 可感知的延迟。
- 权限规则变更后，下一次权限评估即使用新规则（即时生效，见 F6）。
- 系统应在无 Owner 在线时保持可用——等待中的审批请求不应阻塞系统其他功能。
- 沙盒以操作系统级能力强制文件访问范围——Agent 无法通过路径拼接、变形或派生进程绕过。
- 沙盒无法启用时，受沙盒约束的操作一律拒绝执行，不降级为无约束执行。
