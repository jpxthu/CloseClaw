# Message Flow 需求

## 概述

本模块记录一条消息从用户发送到 Agent 回复送达的完整流转过程——覆盖入站（IM → Agent）与出站（Agent → IM）两个方向，串联 IM 平台接入、消息归一化、身份映射、消息路由、会话确定、LLM 对话、渲染与平台发送各环节，供理解完整产品流程时参考。

## 功能需求

### F1. 入站链路

一条用户消息从 IM 平台到达 Agent 的完整步骤：

1. 用户在 IM 平台（飞书、Discord、Telegram 等）发送消息。
2. IM 平台事件到达平台插件，平台特有字段被解析。
3. 消息归一化为统一格式（平台标识、发送者、会话对端、账号标识、消息正文）。
4. 归一化中的账号标识由发送者经身份映射解析得到（发送者 → CloseClaw User），走「IM 用户 → User」入站方向。
5. 空消息丢弃、消息类型识别；非斜杠的文本消息进入 LLM 对话流程，以 `/` 开头的消息由斜杠指令流程处理。
6. 消息路由到 Agent——走「机器人 → Agent」入站方向，由接收方机器人解析出路由目标 Agent。
7. 在该 Agent 范围内按四项标识（平台标识、发送者（IM 侧身份）、会话对端、账号标识（CloseClaw User））共同确定 Session，按下列情形之一处理：
   - 存在未归档 Session：复用其中最后活跃时间最新的一个；
   - 存在归档中 Session：等待归档完成后恢复；
   - 存在已归档 Session：恢复；
   - 上述均无：创建新 Session。
8. LLM 对话：System Prompt 组装 + 历史 + 新消息 → 流式输出。

### F2. 出站链路

Agent 回复从生成到送达用户的完整步骤：

1. 流式输出按格式自动选择渲染：纯文本以轻量文本消息发送，含格式特征的内容以富格式发送（各平台按自身能力渲染，如飞书卡片）。
2. 出站消息经统一处理（频率限制、敏感操作审计、错误降级），发送后追加到 Session 历史。
3. 选择发送机器人——走「Agent → 机器人」出站方向。
4. 渲染与发送分离，经平台 API 发送。
5. 话题型消息携带话题标识，定向回复到对应 Session 的话题。

### F3. 跨机器人双接收与身份归并

同一条群消息同时 @ 多个机器人时，每个接收方机器人各自收到一份平台事件；事件中的发送者标识与 @ 对象标识随接收方机器人不同而取值不同。这些标识必须由身份映射归并为同一个 CloseClaw User，否则同一用户会在不同机器人下被识别为不同 User 并各自开启 Session。

跨应用身份映射是双向的：入站方向，任一接收方机器人语境下的用户标识都解析回同一个 User；出站方向，同一个 User 可解析到各机器人应用语境下的用户标识（用于选发送机器人、@ 解析）。这些按机器人应用语境区分的用户标识同属同一个逻辑 IM 用户，故不违反「单个 IM 平台下 IM 用户 ↔ User 一一对应」的基数规则（基数规则见 [config §F1](config.md)）。

上述跨应用 ID 隔离与归并是经大量实测才确定的平台行为，以真实采集的平台数据为准；飞书 CLI 实测样本（含同一消息被两个机器人分别接收的跨应用 ID 对照事件）见 `tests/fixtures/feishu/cli-poc/`。

> **交叉引用**：身份映射与跨平台归并详见 [permission §F1](permission.md)（身份体系）。

## 非功能需求

- **可靠性**：入站与出站链路的任意环节异常时，系统降级或回滚的边界由各环节对应模块需求文档定义，本模块不重复；各环节的质量期望见对应模块文档。
