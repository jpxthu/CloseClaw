# Daemon 需求

## 概述

Daemon 保障系统的可靠运行：启动时全部组件按依赖顺序初始化完成后才对外提供服务；关闭时安全持久化数据并向 Owner 通知进度；异常中断后衔接恢复流程。关闭与重启过程中，User 的进行中对话与 Agent 的进行中任务得到相应保障（各自的保障与代价见各功能域）。

## 功能需求

### F1. 系统启动

系统启动全流程可控：从进程启动到全部组件（含内部组件与 IM 渠道、CLI 等外部入口）就绪，各组件只在依赖就绪后才被初始化；全部外部入口就绪后，系统才开始接收和处理消息。

### F2. 优雅关闭

Owner 可以通过系统信号（经 CLI 触发，见 [cli §F3](cli.md)（Daemon 生命周期管理））触发优雅关闭。优雅关闭流程：

- 关闭一旦开始，系统不再接收新消息
- 关闭开始时系统已接收、尚未处理完的消息不得静默丢弃，须满足其一：在系统重启后恢复处理；或明确告知 User 该消息未被处理、需重新发送
- 正在进行的 Session 允许完成当前工作。等待条件 = LLM 推理 OR 同步工具等结果 OR 后台任务（Agent 异步调用的工具）OR 子 Session。四个活跃维度由 [session §F11](session.md)（Session 活跃维度）定义。任一维度为 true 则等待其完成；四维全 false 则该 Session 已就绪，关闭流程中不再等待
- 新的 LLM 轮次不再触发；系统重启、Session 恢复后，由 User 的下一条消息按 Session 上下文继续
- 所有 Session 数据在关闭前持久化到存储
- 在途的出站消息（已生成、尚未发送完成）发送完成后，系统才关闭出站通道

Owner 可以在优雅关闭等待期间随时切换为强制关闭（方式详见 F3）。

### F3. 强制关闭

Owner 可以在优雅关闭等待期间再次发送关闭信号，或在关闭进度通知中选择「强制关闭」，立即终止系统：

- Session 内正在执行的工具调用被终止
- 正在进行的 LLM 请求被取消，尚未完成写入 Session 记录的响应内容不再保留（含已生成但未发送的中间内容；已发送给 User 的部分保留）
- 因跳过 F2 的持久化流程，未持久化的 Session 数据在关闭最后阶段兜底持久化
- Owner 接受强制关闭带来的工具副作用（如编译到一半的文件状态不可控）

系统级后台任务仍按 F5 的停止流程处理（强制关闭路径下跳过等待环节、直接快速终止），与上述 Session 侧终止是两条独立路径。

系统下次启动时由 Session 恢复机制处理强制关闭遗留的未完成操作。

> **交叉引用**：强制关闭遗留未完成操作的恢复处理详见 [session §F7](session.md)（运行健康与安全）。

### F4. 关闭进度可见性

Owner 可以在优雅关闭期间看到实时进度：哪些 Session 还在活跃、各自当前状态（LLM 输出中/同步工具执行中/后台任务运行中/子任务进行中/已就绪，对应 [session §F11](session.md)（Session 活跃维度）的四个维度）、等待时长。Owner 可以通过进度通知选择"继续等待"或"强制关闭"。

进度信息在 Session 状态变化时更新；无状态变化期间，系统也应以稳定周期持续更新，让 Owner 能确认系统仍在关闭中而非卡死（更新周期取自设计，保证 Owner 可以及时感知）。

### F5. 系统级后台任务生命周期

系统级后台任务在系统启动时自动运行、关闭时有序停止：正在执行的任务应有机会自行结束；未及时完成的任务被终止后不应留下副作用。全部系统级后台任务停止后不应残留未完成的工作。

系统级后台任务指由系统自身调度、非 Agent 触发的后台任务（如会话归档、完成通知补推与僵死检测、记忆挖掘、配置监听等），与 [session §F11](session.md)（Session 活跃维度）中 Agent 异步调用工具对应的「后台任务」是不同概念。系统级后台任务在关闭中的有序停止按本节执行，与 [F2](#f2-优雅关闭)（优雅关闭）中正在进行的 Session 的等待条件是两条互相独立的收尾路径。

### F6. 配置触发的网关重启

配置变更中需要重启 Gateway 才能生效的一类（重启生效类，判定标准见 [config §F7](config.md)（生效机制与重启类判定），变更监听见 [config §F4](config.md)（配置重载）），由 daemon 择机自动执行无损重启，无需 Owner 手动操作。

- 变更确认后系统进入待重启状态，等待择机窗口：所有 Session 的四维活跃维度均为否（活跃维度定义见 [session §F11](session.md)（Session 活跃维度））即满足窗口条件；无活跃 Session 时立即重启
- 待重启状态下系统正常运行：Session 正常处理消息，新消息不受影响；重启未执行前配置变更未生效，系统按旧配置继续运行
- 择机窗口满足后执行重启。执行中的出站消息按优雅关闭流程处理（见 F2）
- 窗口期内新增的重启生效类配置变更与待执行的重启合并为一次，不重复重启
- 重启完成后通过 IM 向 Owner 发送重启完成通知，附带本次生效的配置变更概要
- 重启执行失败时向 Owner 发送失败通知（含失败原因），不得静默失败
- 无窗口兜底：只要有 Session 处于活跃状态，系统持续等待，不强制打断任何 Session；Owner 可以随时改用强制关闭（见 F3），立即按强制关闭终止系统，本次待执行的重启随之取消

> **交叉引用**：重启生效类配置变更的判定与变更监听详见 [config §F4](config.md)（配置重载）。
> **交叉引用**：重启执行期间的入站消息处理详见 [gateway §F6](gateway.md)（入站消息队列与过载保护）。

## 非功能需求

- 系统启动初始化应在依赖就绪后尽快完成：耗时由依赖决定的层级并行初始化决定，不因组件数量或外部条件引入额外的、与依赖无关的等待
- 优雅关闭不应无感知地无限等待——Owner 可以感知长耗时 Session 的存在并自主决定继续等待或强制关闭；系统不设自动超时，等待时长由 Owner 掌控
- 关闭进度通知应在关闭流程开始后立即推送给 Owner，不应有可感知的延迟
